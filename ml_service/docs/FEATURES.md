# Feature dictionary: Kaggle provider-fraud pipeline

_Generated by `scripts/render_feature_docs.py` from the specs in `fraud_ml/features_provider.py` and `fraud_ml/features_claim.py`. Edit the code, not this file._

> `PotentialFraud` is a **provider-level** label of **undocumented provenance**. It is the supervised target only, never an input, and it is not a verified fraud finding.

## Prediction time

| Model | Unit | Scored when | May use |
|---|---|---|---|
| Supervised (LR / RF / XGBoost) | Provider | End of the observation period | That provider's claims in the period, its patients' profiles, label-free network counts, reference statistics fitted on training providers |
| Isolation Forest | Claim | When the claim is submitted | The claim's own fields, the patient's clinical profile, that patient's claims on **earlier dates**, reference statistics fitted on training providers |

## Excluded from all model inputs

| Item | Reason |
|---|---|
| `PotentialFraud`, and anything computed from labels (e.g. the share of a physician's providers that are flagged) | Target leakage. Shared patients and physicians would carry test labels into training. |
| `Race`, `Gender` | Sensitive attributes. Also, their codes are undocumented. These columns are not even loaded. |
| `DOB` / patient age | Sensitive demographic attribute (age); excluded under the project's fairness rule |
| `State`, `County` as categories | Geography can stand in for demographics. Only the *count* of distinct states a provider serves is used. |
| Inpatient `DeductibleAmtPaid` | Constant (1068), so it carries no information |
| Outpatient procedure codes | Present on under 0.1% of outpatient claims |
| Kaggle "Test" files | Unlabelled. They share patients with the labelled files. Not used. |
| Patient annual totals, in claim-level features | Year-end values that include later claims (future information) |
| Provider identity or aggregates, in claim-level features | Would turn the claim-level anomaly model into a provider model |

## Data-processing approach

1. **Loading:** only the needed columns are read; IDs and codes are stored as `category`, numbers as 32-bit. 558k claims take about 106 MB, and the whole preparation runs in about 12 s.
2. **Cleaning (row-by-row, nothing learned):** inpatient and outpatient claims are stacked with a flag; chronic-condition codes 1/2 become 0/1 (1 = present, by CMS convention, which this dataset doesn't document); renal Y/0 becomes 0/1; negative annual totals are clipped to 0 and flagged; claim duration and length of stay are derived.
3. **Missing values:** these are structural, so they become counts and flags. Documented defaults: 0 when a provider has no claims of a type, 400 days when there is no repeat or earlier claim. Nothing is imputed from statistics.
4. **Duplicates:** there are no exact duplicate rows. Near-duplicates and same-day repeats are **features**, not deleted.
5. **Outliers:** kept, since unusual amounts are exactly the signal. Amounts are `log1p`-transformed. Scale-sensitive models get standardisation fitted inside each training fold.
6. **Learned statistics** (primary-code frequency, a code counts as rare below 5; median amount per claim type and code or DRG) are fitted **on training providers' claims only**, and refitted inside each CV fold.
7. **Split:** stratified by provider label; 15% of providers are held out as the final test set, plus 5-fold stratified CV on the rest (seed 42). Each provider and all its claims sit in exactly one partition. The test set is not used for selection, tuning or thresholds.
8. **Class imbalance (9.35% positive):** class weights / `scale_pos_weight`; thresholds chosen on out-of-fold predictions; PR-AUC, recall and precision reported alongside accuracy.
