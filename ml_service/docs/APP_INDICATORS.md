# Application-native risk indicators (`app-indicators-v2` v2.0.0)

_Generated by `scripts/render_indicator_docs.py` from `app_risk/`. Edit the code, not this file._

> Indicators are transparent statistics computed from this application's data with documented, configured thresholds. They are not machine-learning predictions, not probabilities and not evidence of fraud. Review priority only orders the review queue; it never approves or rejects a claim.

## Data used (read-only, column-whitelisted)

| Query | SQL |
|---|---|
| claims | `SELECT CLAIM_ID, CLAIM_DATE, CLAIM_AMOUNT, DIAGNOSIS, POLICY_ID, PROVIDER_ID FROM CLAIM` |
| policies | `SELECT POLICY_ID, POLICY_TYPE, START_DATE, END_DATE, COVERAGE_AMOUNT, PATIENT_ID FROM POLICY` |
| providers | `SELECT PROVIDER_ID, PROVIDER_TYPE FROM MEDICAL_PROVIDER` |
| rule_hits | `SELECT cr.CLAIM_ID, cr.RULE_ID, fr.RULE_NAME FROM CLAIM_RULE cr JOIN FRAUD_RULE fr ON cr.RULE_ID = fr.RULE_ID` |

Never loaded or used: `ADDRESS`, `APPROVED_AMOUNT`, `DOB`, `EMAIL`, `FIRST_NAME`, `GENDER`, `LAST_NAME`, `STATUS` (post-review decisions would leak the outcome; patient personal or sensitive fields are not needed). The loader rejects data containing them, and the MySQL session is read-only.

## Two timelines (claim level)

1. **Knowledge:** the claims visible in one consistent, read-only database snapshot taken at assessment time (`START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`). Nothing outside the snapshot is used.
2. **Service date:** within the snapshot, comparisons use `CLAIM_DATE` only:
   - prior-history indicators use snapshot claims dated **on or before** the assessed claim's date, excluding the claim itself;
   - duplicate detection uses snapshot claims within **±7 calendar days**.

**`CLAIM_ID` never determines order or history.** It only identifies claims and excludes the assessed claim. Results do not depend on the order in which claims were entered (tested over all insertion orders).

| Property | Behaviour |
|---|---|
| Claims dated more than 7 days after the assessed claim | never change its result |
| A back-dated claim entered later | updates the assessments of the later-dated claims it precedes (new knowledge); earlier snapshots are kept |
| Same snapshot | same result, same digest |

Indicator set 1.0.0 used "`CLAIM_ID` < assessed claim" as history and missed claims entered out of date order. It was never deployed; 2.0.0 replaces it.

## Snapshots, digest and audit trail

Each claim assessment carries `snapshot_claim_count` (claims visible in the snapshot), `prior_history_claim_count`, `comparison_claim_ids` on every indicator (exactly which claims were compared), `indicator_set_version`, `snapshot_taken_at` (MySQL UTC clock at snapshot time) and `indicators_digest`: SHA-256 of the canonical JSON of the deterministic content (claim, indicator set and version, status, rule hits, all indicator results including comparison IDs, triggered count, priority and reasons).

`snapshot_taken_at`, the snapshot counts and the disclaimer are provenance, **not** part of the digest. A claim added anywhere else would otherwise create a new snapshot for every claim, while any change that matters to this claim already changes its indicator values or comparison IDs.

**Append-only:** a new snapshot is stored only when its digest differs from the claim's latest **non-failed** snapshot (`CLAIM_LATEST_VALID_ASSESSMENT`). Snapshots are never updated or deleted (database triggers). The stored `ASSESSED_AT` is set by MySQL (`UTC_TIMESTAMP()`) on insert, as is the outcome's `DECIDED_AT`: one clock for both.

## Training-data rule (Track 3)

**Strict linking only.** An outcome is usable for supervised training only with the **exact snapshot linked to it** (`ASSESSMENT_ID`, the one the investigator was shown), and only if that snapshot belongs to the same claim, is not a failed attempt, and was assessed **at or before** the decision. If the link is absent or invalid, the outcome is **excluded**, with a reason (`no_linked_snapshot`, `linked_snapshot_missing`, `linked_snapshot_other_claim`, `linked_snapshot_failed`, `linked_snapshot_after_decision`). **No other snapshot, older or newer, is ever substituted.** Invalid links are rejected at insert (trigger `trg_cio_valid_snapshot`); the view `OUTCOME_TRAINING_SNAPSHOT` and `app_risk.snapshots.select_training_snapshot` apply the same rule. Historical training features must **never** be recomputed with information entered later.

## Provider level

Claims with `CLAIM_DATE` ≤ the as-of date, compared with peers at the same cutoff (date-based; independent of `CLAIM_ID`).

Dates are calendar dates from MySQL (`DATE`), not converted through any timezone (tested under IST).

## Claim-level indicators

| Code | Name | Inputs | Calculation | Why | Triggered when |
|---|---|---|---|---|---|
| `coverage_share` | Share of policy coverage | CLAIM.CLAIM_AMOUNT, POLICY.COVERAGE_AMOUNT | claim amount / policy coverage amount | A single claim using a large part of total coverage | >= 50% |
| `outside_policy_period` | Claim date outside policy period | CLAIM.CLAIM_DATE, POLICY.START_DATE, END_DATE | days before policy start or after policy end (0 if inside) | Service dated when the policy was not in force (not covered by the SQL rules) | > 0 days |
| `amount_vs_diagnosis_median` | Amount vs earlier-dated claims with the same diagnosis | CLAIM_AMOUNT, DIAGNOSIS (normalized), CLAIM_DATE | claim amount / median amount of snapshot claims with the same diagnosis dated on or before this claim | Billing far above what this diagnosis usually costs here | >= 3x (needs >= 5 earlier-dated claims) |
| `diagnosis_new_for_provider_type` | Diagnosis not seen before for this provider type | DIAGNOSIS, MEDICAL_PROVIDER.PROVIDER_TYPE, CLAIM_DATE | number of earlier-dated snapshot claims with this diagnosis from providers of the same type | Possible mismatch between provider type and diagnosis | = 0 (needs >= 10 earlier-dated claims for the type) |
| `patient_claims_prior_30d` | Patient's other claims in the 30 days up to this claim | PATIENT (via POLICY), CLAIM_DATE | other snapshot claims of the same patient (any policy, any provider) dated within the 30 days up to and including this claim's date | Claim bursts for one patient | >= 3 |
| `days_since_patient_previous_claim` | Days since the patient's previous claim | PATIENT (via POLICY), CLAIM_DATE | days between this claim and the patient's most recent other claim dated on or before it | Rapid repeat visits | <= 7 days |
| `near_duplicate_claims` | Possible duplicate submissions | PATIENT, PROVIDER_ID, DIAGNOSIS, CLAIM_AMOUNT, CLAIM_DATE | other snapshot claims with the same patient, provider and diagnosis, amount within 1%, dated within 7 calendar days before or after | Duplicate or re-submitted bills (in either order) | >= 1 |
| `provider_volume_surge` | Provider's recent claim volume vs its own baseline | PROVIDER_ID, CLAIM_DATE | provider's other claims dated in the 30 days up to this claim / its average 30-day count over days 31-365 before | Sudden increase in a provider's billing | >= 3x and >= 3 claims (needs >= 5 baseline claims) |

Statuses: `ok`; `insufficient_history` (not enough earlier data, so `triggered` is null); `not_applicable` (e.g. no previous claim). Insufficient history is never filled with a default.

### Review priority (ordering aid, not a score or a decision)

- **High:** any existing SQL rule hit on the claim, or ≥ 2 triggered indicators
- **Elevated:** exactly 1 triggered indicator
- **Routine:** otherwise

Reasons are always listed. Priority never changes `CLAIM.STATUS` and never approves or rejects a claim.

## Provider-level indicators

Ratio indicators need ≥ 5 claims. Peer comparison needs ≥ 10 other providers with ≥ 5 claims; "unusually high" means above the peers' 90th percentile, and "unusually low" below their 10th.

| Code | Name | Calculation | Peer comparison |
|---|---|---|---|
| `claim_count` | Claims | claims dated on or before the as-of date | informational |
| `distinct_patients` | Distinct patients | patients (via policy) with at least one claim | informational |
| `active_months` | Active months | calendar months with at least one claim | informational |
| `claims_per_patient` | Claims per patient | claims / distinct patients | flag if unusually high |
| `claims_per_active_month` | Claims per active month | claims / active months | flag if unusually high |
| `share_same_day_repeat` | Same-day repeat claims | claims where the same patient has another claim at this provider on the same date / claims | flag if unusually high |
| `median_days_between_patient_claims` | Median days between a patient's claims | median gap between consecutive claims of the same patient at this provider | flag if unusually low |
| `share_patients_3plus_claims` | Patients with 3+ claims | patients with >= 3 claims at this provider / patients | flag if unusually high |
| `patient_mean_other_providers` | Patients shared with other providers | mean number of OTHER providers each of this provider's patients also claimed through | flag if unusually high |
| `rule_flag_rate` | Claims flagged by SQL rules | claims with >= 1 CLAIM_RULE hit / claims (existing rule engine output) | flag if unusually high |

Provider-level and claim-level results are reported separately and never combined into one number.
